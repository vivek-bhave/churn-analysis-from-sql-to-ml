# SHAP Explainability Service

The **SHAP Explainability Service** provides feature-level explanations for every prediction generated by the Decision Support System. Instead of returning only churn probabilities, the backend identifies **which customer characteristics contributed most** to the prediction and whether each feature increased or decreased churn risk.

The explainability service is designed to work with both machine learning models used in the backend while exposing a consistent explanation format to the frontend.

---

## Purpose

The SHAP Explainability Service performs four responsibilities:

* Generate feature-level explanations for model predictions.
* Quantify the contribution of each customer feature.
* Identify whether each feature increases or decreases churn risk.
* Return a normalized explanation format independent of the underlying ML model.

This allows customer support agents and managers to understand **why** a customer received a particular prediction instead of treating the model as a black box.

---

## Explainability Pipeline

`Validated Customer Features → Model Preprocessor → SHAP Explainer → Feature Contributions → Aggregation → Relative Importance → Risk Direction`

---

## Model Initialization

The backend loads both trained machine learning pipelines during application startup.

| Component                    | Purpose                                                   |
| ---------------------------- | --------------------------------------------------------- |
| Logistic Regression Pipeline | Retention prediction explainability.                      |
| XGBoost Pipeline             | Churn prediction explainability.                          |
| Preprocessors                | Transform categorical features into encoded model inputs. |
| SHAP Explainers              | Compute feature contribution values for each model.       |

Both SHAP explainers are initialized once during startup, avoiding repeated initialization during API requests and reducing inference latency.

---

## Background Dataset

SHAP requires a reference distribution to measure how much each feature contributes to a prediction.

Two background datasets are stored inside the `Models/` directory.

| Background Dataset       | Used By                            |
| ------------------------ | ---------------------------------- |
| `shap_background_lr.csv` | Logistic Regression SHAP Explainer |
| `shap_background_xg.csv` | XGBoost SHAP Explainer             |

The background data represents typical customer feature distributions used as the baseline for computing SHAP values.

## Logistic Regression Explainability

### Input

The Logistic Regression explainer receives the same engineered features used during model training.

| Features        |
| --------------- |
| Issue Level     |
| Delay Level     |
| Spend Level     |
| Contract Length |

### Processing Logic

1. Transform customer features using the trained preprocessing pipeline.
2. Compute SHAP values using **LinearExplainer**.
3. Match SHAP values with transformed feature names.
4. Aggregate encoded features back into business-friendly feature groups.

### Feature Aggregation

One-hot encoded categorical variables generate multiple SHAP values for a single business feature.

For example:

| Encoded Features   | Aggregated Feature |
| ------------------ | ------------------ |
| Issue_Level_High   | Issue Level        |
| Issue_Level_Medium | Issue Level        |
| Issue_Level_Low    | Issue Level        |

The backend sums these contributions so users see explanations at the business feature level rather than encoded columns.

### Output

The Logistic Regression explainer returns four explainable business features with contribution scores, relative importance percentages, and risk directions.

## XGBoost Explainability

### Input

The XGBoost explainer receives the complete engineered customer profile used by the churn prediction model.

| Feature Groups         |
| ---------------------- |
| Issue Level            |
| Delay Level            |
| Spend Level            |
| Contract Length        |
| Age Group              |
| Last Interaction Level |
| Tenure Level           |
| Usage Frequency Level  |
| Gender                 |
| Subscription Type      |

### Processing Logic

1. Transform customer features using the XGBoost preprocessing pipeline.
2. Compute SHAP values using **TreeExplainer**.
3. Map SHAP values to transformed feature names.
4. Aggregate encoded categorical features into business-friendly feature groups.

### Feature Aggregation

The backend combines multiple encoded SHAP values into a single contribution for each original customer feature, producing explanations that align with customer-facing business concepts instead of one-hot encoded variables.

## Feature Aggregation Strategy

### Why Feature Aggregation is Required

Both machine learning pipelines use **one-hot encoding** for categorical features during preprocessing. As a result, SHAP generates contribution values for the encoded columns instead of the original business features.

For example, the single business feature **Issue Level** is transformed into multiple encoded features:

| Encoded Feature | SHAP Value |
|-----------------|-----------:|
| Issue_Level_High | 0.42 |
| Issue_Level_Medium | -0.08 |
| Issue_Level_Low | 0.00 |

While these values are correct from the model's perspective, they are **not intuitive for customer support staff or managers** who need to understand which business feature influenced the prediction.

### Aggregating Encoded Features

To improve interpretability, the backend **sums the SHAP values of all encoded columns belonging to the same original feature** and produces a single contribution score.

For example:

```text
Issue Level Contribution
= SHAP(Issue_Level_High)
+ SHAP(Issue_Level_Medium)
+ SHAP(Issue_Level_Low)

= 0.42 + (-0.08) + 0.00
= 0.34
```

The final explanation contains one contribution value for **Issue Level** instead of three separate encoded columns.

This aggregation is performed for every categorical feature, including Contract Length, Spend Level, Subscription Type, Tenure Level, Age Group, and others.

### Why Relative Contribution Percentage is Calculated

Raw SHAP values indicate the direction and magnitude of influence, but they are difficult to compare directly because different predictions produce different SHAP scales.

The backend therefore converts aggregated SHAP values into **relative contribution percentages** using the absolute contribution of each feature.

<math block value="\\text{Relative Contribution} = \\frac{|\\text{Feature SHAP}|}{\\sum |\\text{All SHAP Contributions}|} \\times 100"/>

This normalization provides an intuitive explanation of **how much each feature contributed to the churn prediction**.

### Example

| Feature | Aggregated SHAP | Relative Contribution |
|---------|----------------:|----------------------:|
| Issue Level | 0.34 | 34% |
| Delay Level | 0.22 | 22% |
| Tenure Level | -0.18 | 18% |
| Spend Level | -0.15 | 15% |
| Remaining Features | 0.11 | 11% |

### Design Decision

The backend intentionally returns **aggregated business features** and **relative contribution percentages** because they are significantly easier to interpret in real time than individual one-hot encoded SHAP values. This allows customer support agents and managers to immediately identify the primary drivers behind a churn prediction without understanding the underlying feature encoding used by the machine learning models.

### Output

The XGBoost explainer returns contribution scores for ten business features representing customer behaviour, demographics, subscription information, and engagement history.

---

## Relative Feature Contribution

Raw SHAP values indicate contribution magnitude but are difficult to compare directly across features.

The backend converts contributions into **relative contribution percentages** by dividing the absolute contribution of each feature by the total absolute contribution across all features.

This normalization provides an intuitive ranking of feature importance for a single prediction.

| Feature            | Relative Contribution |
| ------------------ | --------------------- |
| Payment Delay      | 32%                   |
| Issue Level        | 24%                   |
| Tenure Level       | 18%                   |
| Remaining Features | Remaining Percentage  |

The percentages sum to approximately **100%** for each prediction.

---

## Risk Direction Calculation

Each aggregated SHAP value is converted into a business-friendly direction.

| SHAP Value            | Direction        |
| --------------------- | ---------------- |
| Positive Contribution | `increases_risk` |
| Negative Contribution | `decreases_risk` |

This allows the frontend to clearly communicate whether a customer characteristic pushes the prediction toward churn or toward retention.

---

## Model Routing Strategy

The backend executes both machine learning models during prediction but generates SHAP explanations from **only one model**.

| Prediction Result               | SHAP Explainer Used      |
| ------------------------------- | ------------------------ |
| Customer predicted as Churn     | XGBoost SHAP             |
| Customer predicted as Non-Churn | Logistic Regression SHAP |

This routing strategy ensures that explanations always correspond to the model responsible for the prediction presented to the user.

---

## API Response Structure

The SHAP service returns a standardized JSON structure regardless of which model generated the explanation.

```json
{
  "contributions": {
    "Issue_Level": 0.41,
    "Delay_Level": 0.28,
    "Spend_Level": -0.16,
    "Contract Length": 0.09
  },
  "relative_contributions": {
    "Issue_Level": 43.2,
    "Delay_Level": 29.5,
    "Spend_Level": 16.8,
    "Contract Length": 10.5
  },
  "directions": {
    "Issue_Level": "increases_risk",
    "Delay_Level": "increases_risk",
    "Spend_Level": "decreases_risk",
    "Contract Length": "increases_risk"
  }
}
```

This consistent response format allows the frontend to visualize feature importance without knowing which underlying machine learning model produced the explanation.

---

## Design Decisions

| Decision                                | Rationale                                                                          |
| --------------------------------------- | ---------------------------------------------------------------------------------- |
| Separate SHAP Service                   | Keeps explainability independent from prediction logic.                            |
| LinearExplainer for Logistic Regression | Efficient and appropriate for linear models.                                       |
| TreeExplainer for XGBoost               | Designed for tree-based ensemble models.                                           |
| Aggregate One-Hot Encoded Features      | Presents explanations using original business features instead of encoded columns. |
| Relative Contribution Percentages       | Makes feature importance easier to interpret visually.                             |
| Standardized JSON Output                | Frontend remains independent of the underlying explainability implementation.      |

---

## Output of the Explainability Service

The SHAP Explainability Service produces a model-agnostic explanation containing:

* Feature contribution scores.
* Relative feature importance percentages.
* Risk direction for each feature.

These explanations are included in the unified API response and help customer support teams understand the reasoning behind every churn prediction.
